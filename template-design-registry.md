### Header component changelog (applies to all pages in this template)
The header went through two corrective revisions after initial launch — noted here so future templates don't repeat the same mistakes:
1. **Grid → Flex:** original header used `grid-cols-3` (three *equal* thirds: left-nav / centered-logo / right-nav+controls). Equal-thirds tracks don't grow to fit content — the right column (nav + icons + CTA) needed far more than 1/3 of the header width at realistic desktop sizes, overflowing and visually overlapping the centered logo. Replaced with a single flex row (logo `shrink-0` + nav `flex-1` + controls `shrink-0`) sized by actual content, not arbitrary fractions.
2. **Breakpoint lg → xl:** even the corrected flex layout was razor-thin at 1024px (`lg`) with 6 nav links; adding a 7th link (Home 2) would have overflowed again. Desktop nav/CTA now gate on `xl` (1280px) instead of `lg` (1024px) — tablet-landscape widths (1024–1279px) now correctly get the hamburger drawer instead of a cramped nav row. `DESKTOP_BREAKPOINT` in `main.js` was updated to match (1280).
Also fixed: the header's transparent-over-hero state (home page only) was replaced with a permanent semi-opaque glass background on every page, since dark nav text over a busy/dark hero photo was unreadable; and the mobile drawer's RTL "closed" position (`translateX(-100%)`) was removed entirely because it wasn't matched by an equal flip of the drawer's physical docking side (`right-0`), which pulled the panel partially into view the instant RTL was toggled — the drawer now always docks and slides from the right regardless of direction.

### Gallery Page redesign (`gallery.html`)
Redesigned after initial launch — replaced the original asymmetric "editorial" grid (one `col-span-2 row-span-2` featured tile + one `col-span-2 aspect-video` tile among plain squares) with a **uniform grid**: every tile is the same `aspect-[4/5]`, so the CSS grid auto-flow can never leave a gap or an incomplete row, in any filtered state, at any breakpoint. The asymmetric layout was the root cause of the original imbalance — with irregular tile spans, categories couldn't be filtered to an even, gap-free layout no matter how many photos each had.
- **Photo count:** Every category now holds exactly **4 photos** (16 total, was 4/3/3/2 unevenly). 4 new content-verified images were sourced via Unsplash search (not guessed IDs) to fill the gaps: one playground photo, one art-activity photo, two meal-time photos.
- **Filter tabs:** Each tab now shows a live photo count badge (`data-filter-count`, computed from the DOM at runtime, not hardcoded) — e.g. "Meals ⸱" — plus a category icon. Active tab styled via a new `.gallery-filter-btn[aria-selected="true"]` state (coral fill + bottom-shadow, distinct from the `tab-btn` class used for the age-group tabs elsewhere).
- **Category badge chips:** Each tile carries a small always-visible color-coded pill top-left (sky=Classroom, leaf=Playground, coral=Activity, sunshine=Meal Time) so the category reads at a glance even before hovering — new pattern, not used elsewhere in the template.
- **Load More pagination:** `data-gallery-grid` + `data-batch-size="8"` drive a JS batching system (`initGalleryFilter` in `main.js`, rewritten): "All Photos" shows 8 initially with a "Load More Photos" button revealing the rest; switching to any single-category filter shows all 4 of that category directly (no pagination needed for a set that small) and hides the Load More button; returning to "All Photos" resets the batch. A live `data-gallery-count` label ("Showing 8 of 16 photos") tracks the current state.
- **Reveal animation:** New `.gallery-tile` / `.gallery-tile-visible` CSS pair (opacity + translateY + scale transition) replaces the old instant `display:none` toggle — items entering view (via filter change or Load More) now fade/rise in smoothly instead of popping. Deliberately *not* wired through GSAP ScrollTrigger's `data-reveal` system, since ScrollTrigger initializes against an element's layout box at scan time and this grid's items are frequently `display:none` at load (everything past batch 1) — mixing the two would have produced unreliable trigger positions.

**Gallery page content expansion** (second pass, same file): the page went from "hero + filter grid + one-line CTA" to a full campus-life showcase. ### Header, mobile-menu & lightbox changelog (fixes applied after initial launch)
Three corrective revisions, recorded so future templates don't repeat the same mistakes:
1. **Split-nav → logo-left:** the original "centered-logo, split-nav-either-side" header was replaced with a conventional logo-left / centered-nav-links / right-controls layout, at explicit user request. Logo position is now identical on mobile and desktop (far left) rather than centering only on desktop and left-aligning only on mobile.
2. **Nav-link centering:** the centered nav-links group was initially left-aligned immediately after the logo (`flex-1` container, links packed to its start); changed to `justify-center` so the links center within the space between the logo and the right-side controls, per explicit request.
3. **GLightbox blank popup:** gallery images hosted on Unsplash have no file extension in the URL (`?auto=format&fit=crop&w=1400&q=80`), so GLightbox couldn't auto-detect them as images and rendered an empty iframe on click. Fix: every `.glightbox` anchor's `data-glightbox` attribute must include an explicit `; type: image` (e.g. `data-glightbox="title: Nursery Room; type: image"`) whenever the image URL lacks a recognizable extension.
4. **RTL skip-link scroll-width explosion:** the accessibility skip-link used the classic `left: -9999px` off-screen-hiding technique. Under `dir="rtl"`, the browser's overflow/scrollWidth calculation folds that huge negative offset into `document.scrollWidth` (observed: exactly `9999 + viewport-width`), which pushed the entire visible viewport off to a blank stretch of the inflated canvas — the whole page (not just the skip-link) appeared to render blank whenever RTL was toggled with the mobile menu open. Fix: hide the skip-link with `transform: translateY(-100%)` instead of a large negative `left` offset — no large offsets anywhere means nothing for RTL's overflow recalculation to inflate. **Lesson for future templates: never use `left: -9999px` (or any large fixed-pixel physical offset) for visually-hidden-until-focused elements on a template that supports RTL — use a transform-based hide instead.**
5. **Dropdown click-vs-hover race:** an early version of the desktop "Home" dropdown toggled open/closed on click while *also* opening on `mouseenter` / closing on `mouseleave`. A mouse user hovering (opens it) then clicking (toggle → closes it) got a dropdown that closed on click. Fix: click now always calls `open()` (never toggles), and closing is delegated entirely to `mouseleave`, outside-click, `focusout`, and Escape — click and hover no longer fight each other.
6. **Hero decorative shapes bleeding through the translucent header:** two of `index.html`'s floating cloud/star SVGs sat at `top-16`/`top-24` relative to the hero section — but since the header is `position: fixed` (removed from document flow), the hero section's own top edge is at document y=0, not below the header. At `lg`+ widths those shapes rendered underneath the header's `bg-white/95 backdrop-blur-md`, faintly bleeding through as a ghost artifact only visible on close inspection. Fix: pushed both shapes further down (`top-16`→`top-32`, `top-24`→`top-36`) to clear the header's ~92–104px height with margin. **Lesson: any absolutely-positioned decorative element inside the first section after a `position: fixed` header needs a `top` offset comfortably larger than the header's total height, since the section's own coordinate origin starts at the true document top, not visually below the header.**
7. **Mobile drawer content pinned to one edge at tablet widths:** per an explicit requirement the overlay itself must stay 100% width at every breakpoint, but the nav content inside it was `items-end`/`text-right` unconditionally — great on a 320–425px phone, but at 768–1279px (tablet, still below the `xl` hamburger cutoff) it left the content pinned to the far right of a mostly-empty full-width canvas. Fix: `items-end sm:items-center` + `text-right sm:text-center` (nav, the Home-submenu wrapper, and its panel) — right-aligned on phone widths, centered from `sm` (640px) up, while the overlay itself never stops being 100% width. Both requirements ("100% width" and "properly aligned on tablet") are satisfied simultaneously because they're about content alignment vs. container width — not the same property.
8. **`gallery.html` missing GSAP/ScrollTrigger includes:** the original gallery page never used scroll-reveal animation, so it never loaded the GSAP/ScrollTrigger `<script>` tags every other page includes. When later content sections were added using the site's standard `data-reveal` / `data-reveal-number` attributes, `initScrollReveals()` silently no-op'd (`typeof gsap === 'undefined'` guard) — the new sections just appeared statically (harmless) but the animated stat counters stayed frozen at their literal `0` fallback text forever (not harmless — a visibly broken counter). Fix: added the two missing script tags. **Lesson: `data-reveal*` attributes are inert markup, not a self-contained feature — always confirm the GSAP/ScrollTrigger scripts are actually present on a page before using them, especially when extending a page that predates the site's animation system.**
9. **Confirmed a genuine image/caption mismatch, and found a reliable way to catch more:** `about.html`'s new Learning Approach section used `photo-1497633762265-9d179a990aa6` captioned "Teacher guiding preschoolers through a hands-on classroom lesson" — an ID picked from memory very early in this project, before the site adopted Unsplash-search-then-verify sourcing. The rendered photo was actually a stack of colored books. Caught it by eye in a full-page review screenshot, not by any automated check (HTTP 200 + a WebFetch text description of the *search results page* both said nothing about the *actual photo's contents*). **Working technique discovered while fixing this: `WebFetch` can't describe an image URL directly (it only sees encoded binary and says so) — but it silently saves that binary to a local `.jpg` in the tool-results folder every time, and the `Read` tool *can* view that saved file. So `WebFetch` on the raw `images.unsplash.com/photo-…` URL (any prompt) → `Read` on the path it reports saving to, is a real way to visually verify a specific candidate image before committing to it, not just trust its alt-text search description.** Replaced with `photo-1761208662734-fb46f1398551`, verified this way before use. Apply this fetch-then-Read check to any image sourced from memory or from a search-results description rather than viewed directly — search descriptions describe the search snippet, not necessarily what's in the full-resolution photo.

10. **LTR mobile/tablet hamburger-left fix regressed RTL:** to move the hamburger to the left / logo to the right on mobile/tablet in LTR, the previous fix removed the hamburger's old unconditional `ml-auto` and replaced it with `ltr:order-1` / `ltr:order-2 ltr:ml-auto` (scoped only to `dir="ltr"`). This fixed LTR but left RTL with *no* edge-anchoring at all below `xl`: both elements defaulted to `order: 0` and sat packed together at the flex-start side (visually the right, since RTL mirrors `flex-direction: row`), leaving a large dead gap on the opposite side — exactly the bug in the reported screenshot. **Fix: added `justify-between` to the header's main flex row** (`<div class="flex items-center gap-4">` → `...justify-between gap-4`). This is direction-agnostic — `justify-content: space-between` always anchors the first and last flex-order items to the start/end edges, and "start/end" already flip correctly with `dir` on their own. Combined with the existing `ltr:order-1`/`ltr:order-2` swap (which only needs to override *which* element is first/last, not push anything to an edge), both directions now anchor correctly with no extra `ltr:`/`rtl:` duplication needed for the edge-pinning itself. At `xl`+ this has no effect, since the `flex-1` nav already consumes all free space regardless of `justify-content`. **Lesson: when reversing a two-element edge-pinned layout for only one text direction, prefer `justify-between` (inherently bidi-correct) over an `auto`-margin scoped to a single `dir:` variant — a scoped auto-margin fixes the direction you tested and silently strips the other direction's spacing if it was relying on that same margin before.**

### Content-accuracy note (image sourcing)
An initial pass populated photo placeholders with Unsplash `photo-<id>` URLs recalled from memory and verified only by HTTP 200 status — several turned out to depict unrelated subjects once rendered (a library interior captioned "Pre-K Classroom," a magnifying glass on a laptop captioned "Story Time," a street-photography shot in a gallery grid). HTTP 200 confirms a URL *resolves*, not that its *content* matches the caption. The fix: use `WebFetch` on Unsplash search-results pages (e.g. `unsplash.com/s/photos/preschool-classroom`) to extract real `images.unsplash.com/photo-…` URLs paired with their actual alt-text descriptions, then verify those specific URLs return 200 — only then treat an image as content-verified. Every photo in this template was re-sourced this way. Apply this method from the start on future templates rather than as a corrective pass.

### Cross-page image de-duplication pass

### Horizontal scroll strips unusable with a desktop mouse
Several sections (`index.html`'s facility gallery preview, `home-2.html`'s daily-activities strip, `about.html`'s milestones timeline, `gallery.html`'s testimonial strip) use `overflow-x-auto no-scrollbar` — deliberately hiding the scrollbar for a cleaner look. This left desktop mouse users with **no way to reach the overflow content at all**: a mouse only produces a vertical wheel delta, which just scrolls the *page* past the section, and there's no visible scrollbar to drag since it's hidden by design. Touch and trackpad users never noticed since horizontal swipe gestures work natively. Confirmed via a Playwright test *before* fixing: `scrollWidth` (1424px) genuinely exceeded `clientWidth` (1280px) — extra content existed and was permanently unreachable by mouse.
- **Fix, centralized in `main.js`/`style.css` rather than per-page** (`initHorizontalScrollStrips()`, applied via the generic `.overflow-x-auto.no-scrollbar` selector so it automatically covers every current and future strip using this pattern, no per-page wiring needed): a `wheel` listener redirects vertical wheel delta into `scrollLeft` and calls `preventDefault()` so the page itself stops scrolling while hovering a strip with room left to scroll; a `mousedown`/`mousemove`/`mouseup` set adds click-and-drag scrolling (`cursor: grab` → `grabbing` via a `.is-dragging` class, which also sets `pointer-events: none` on children mid-drag so a card's own hover/link states don't fight the drag); a `moved` flag suppresses the trailing `click` event after an actual drag so dragging a strip never accidentally activates a link/card underneath the cursor, while a plain (non-drag) click still navigates normally.
- **Lesson: `overflow-x-auto` + `no-scrollbar` is a mobile-first pattern that silently fails for desktop mouse users** — if a horizontal-scroll strip needs a hidden scrollbar for visual cleanliness, it needs the wheel-redirect + drag-to-scroll pair (or explicit prev/next buttons) from the start, not just on mobile where native swipe already works. Apply `initHorizontalScrollStrips()`'s selector-based approach on future templates too, since it fixes every matching strip site-wide with zero per-instance markup changes.

### Revision pass — dark-mode color-token bug, button redesign, RTL polish, equal-count grids
A direct follow-up requested three things: refine the theme colors (keep the volt/ink/ember identity), replace the angular cut-corner buttons with a rounded pill shape, and make sure `classes.html`/`gallery.html` show an equal number of cards in every filter category. Auditing the color request surfaced a real pre-existing bug worth recording.

1. **`--ink`/`--chalk` dark-mode contrast bug (found during the color audit, not reported by the user):** both tokens were dual-purposed and collided under `data-theme="dark"`. `--ink` was used everywhere as a *permanent* dark surface color (footer, hero-split, ticker, page-banner-ink, mobile menu, dash-side, brand-mark, `.card-surge-dark`, `.btn-surge-dark`) — but the dark-mode block also redefined `--ink:#f6f6f2` (near-white), so every one of those "always-dark" bands would flip to a *light* background in dark mode. Simultaneously `--chalk` was used both as the adaptive page-background token (correct) **and** as the "light text sitting on a dark band" color in those same components — but `--chalk` itself flips to near-black in dark mode, so the text would go dark-on-dark at the same time the background went light-on-light. Net effect: the footer, the diagonal-split hero, the radial mobile menu, the stat ticker, `dashboard.html`'s sidebar, and six inline `background:var(--ink);color:var(--chalk)` section bands (About/FAQ/Home 2/Home 1/Pricing) would all have rendered as low/zero-contrast in dark mode. **Fix:** added a new permanent token `--brand-light:#f6f6f2` (never redefined in either dark-mode block, alongside `--ink` which simply had its two dark-mode redefinitions deleted so it stays `#14151a` in both themes); every `color:var(--chalk)` usage that meant "light text on a permanently-dark surface" was repointed to `color:var(--brand-light)` (9 CSS rules + the 6 inline HTML bands). `--chalk` itself was left fully reactive for its one legitimate use (`body{background:var(--chalk)}` and the streak-ring-card's page-matching border). Also fixed `.badge-ember`'s dark-mode contrast (`--ember-dark` text was too low-contrast on its own translucent chip in dark mode; added a `[data-theme="dark"]` override to a brighter `--ember`). **Lesson for future templates: a color token that's reused for two different *semantic* purposes (an adaptive one and a fixed one) is a latent dark-mode bug even if it looks correct in light mode — grep every `var(--token)` usage site-wide before assuming a token is safe to redefine per-theme.**
2. **Button redesign:** `.btn`/`.btn-surge`/`.btn-surge-dark`/`.btn-outline` were rebuilt from the angular clip-path + bottom-rise `::before` fill (documented in the original entry above) to a fully rounded pill (`border-radius:999px`) with a lift-on-hover (`translateY(-3px)`) plus a colored glow `box-shadow` and a `filter:brightness()` tweak — no background/color/border swap on hover at all. 3. **Filter-chip active-state bug (found while touching button styles):** `classes.html`'s and `gallery.html`'s category filter chips only ever toggled an `.is-active` class in `main.js`, but no CSS rule styled `.is-active` — so clicking a different chip never visually indicated which filter was selected (only the initial "All" chip, hardcoded with `.btn-surge`, ever looked active). ### Testing & functional-bug changelog (found and fixed via headless-Chrome + Puppeteer interaction testing before sign-off)
Unlike T1/T2 (whose changelogs record fixes made after user reports), this template was interaction-tested end-to-end — dark/light toggle, RTL/LTR toggle, header search, mobile bottom-sheet, category filters, steppers, all three forms, FAQ accordion, and horizontal-overflow checks at 320/375/425/768/1024/1280/1440px on every page — **before** being marked complete, using headless Chrome (`--headless=new --screenshot`) for visual review and a Puppeteer-core driver (pointed at the system Chrome install) for scripted interaction. Three real bugs were caught this way and are recorded here so future templates can watch for the same classes of mistake:
1. **`data-reveal="left"/"right"` scroll-reveal transforms caused permanent horizontal overflow on every page.** The reveal system's initial (pre-intersection) state applies `transform: translateX(±32px)` so elements slide into place. Since this transform is applied to *every* matching element on page load — including ones far below the fold — any element whose untransformed position was already near the left/right edge of the viewport pushed the document's scrollable area past the viewport width from the very first paint, before any scrolling or JS observer had fired. This produced a consistent 8–19px `scrollWidth > clientWidth` overflow at *every* breakpoint on *every* page, confirmed via `document.documentElement.scrollWidth - clientWidth` in a scripted check. **Fix: `overflow-x: hidden` on `html, body`** — this is the standard, defensive counter-measure for exactly this class of bug (any decorative/animation transform that might transiently or permanently extend layout bounds) and was verified to bring overflow to exactly 0px at all 7 tested widths across all 8 pages afterward. **Lesson: any template using transform-based entrance animations (translateX/Y reveal, floating decorative shapes, etc.) needs a global `overflow-x: hidden` safety net, not just careful placement of individual elements — CSS transforms on far-below-fold elements can silently extend `document.scrollWidth` before the user ever scrolls there or the animation resolves.**
2. **Header search overlay had no results container in the markup.** The JS (`initHeaderSearch` → `renderResults`) was written against a `[data-search-results]` selector that was never actually added to the header HTML on any page — the search input and close button existed, but typing produced no visible output at all (a silently-dead feature, not a crash). Caught by a scripted test that typed "milk" and asserted at least one result rendered; it returned zero. **Fix:** added an absolutely-positioned `[data-search-results]` dropdown panel (rounded, bordered, scrollable) as a sibling of the input inside the now-`relative` search-overlay container, on all 7 pages that include the header search. **Lesson: when JS is written against a `data-*` hook, grep the HTML to confirm that hook actually exists before considering the feature done — a missing container fails silently (no console error) rather than loudly.**
3. **Success messages were nested inside the `<form>` they belonged to, so hiding the form on submit also hid its own success message.** The submit handlers in `main.js` (`initForms`, `initBulkOrderForm`) add a `hidden` class to the `<form>` element itself and simultaneously try to reveal a `[data-form-success]` message — but on the general contact form and the bulk-order form, that success `<p>` was a *child* of the form being hidden, so `display: none` on the parent made the success message unconditionally invisible regardless of its own class state. (The two newsletter forms were unaffected — their success message happened to already be written as a sibling *after* `</form>`, which is what exposed the inconsistency.) Caught by a scripted test that submitted valid data and asserted the success message's computed visibility, not just its class list. **Fix:** restructured both affected forms so `[data-form-success]` is a sibling of `<form>` (wrapped in a shared parent `<div>` where needed to preserve grid layout), and updated `main.js` to look up the success element via `form.parentElement.querySelector('[data-form-success]')` instead of `form.querySelector(...)`. **Lesson: never place a "success" confirmation message as a descendant of the form element you plan to hide on success — verify the fix by checking actual rendered visibility (e.g. `!el.classList.contains('hidden')` *and* the element is reachable), not just that the class-toggle code ran without throwing.**

1. **FAQ search had a one-way "ratchet" bug that permanently mis-expanded accordion items.** `page.type()`-style character-by-character input fires an `input` event per keystroke; the original handler set `aria-expanded="true"` on any item matching the *current partial* query but never set it back to `false` when a later, more specific keystroke stopped matching it. Typing "delivery" letter-by-letter (d → de → del → …) transiently matched nearly every FAQ item (most contain the letter "d" somewhere) and force-expanded all of them; by the time the full word landed only 3 items were *visible*, but all ~13 remained `aria-expanded="true"` underneath — confirmed by a scripted check (`TRUE_AFTER_DELIVERY_SEARCH: 13` before the fix). **Fix:** the expand/collapse line changed from `if (match && q) { …aria-expanded, 'true' }` (write-only) to `if (q) { …aria-expanded, match ? 'true' : 'false' }` (always reconciles both directions whenever a query is active). **Lesson: any "auto-expand on search match" feature that fires per-keystroke must also explicitly *un*-expand non-matches on every keystroke, not just expand matches — otherwise state from an earlier, broader partial-query accumulates and never clears.**

### Global policy update — strict image uniqueness, and second premium redesign pass (Home 1, Home 2, Categories, About)
The client issued a standing, template-wide requirement after the first premium-redesign pass: **no image may ever be reused anywhere on the site, even for the same product/category appearing on multiple pages.** This is stricter than the "2-page reuse of a genuinely on-topic photo is acceptable" precedent recorded earlier in this file (T2's registry) — that precedent is superseded *for this template going forward*. Apply the strict no-reuse rule from the start on any future template revision, rather than as a retrofit.

**Audit method (repeatable for future passes):** extract every `images.unsplash.com` / `plus.unsplash.com` URL from every HTML file with a `grep -ohE` sweep, strip query-string noise (`?w=`, `&q=`), `sort | uniq -c`, and any count greater than 1 is a duplicate needing a replacement for every occurrence past the first. This template had **94 total image usages across 8 pages, of which 27 distinct photo IDs were each reused 2–5 times — 46 individual occurrences needed a fresh, unique replacement.** For each duplicate group, one occurrence was designated the "keeper" (kept unchanged) and every other occurrence got a newly-sourced photo, with accurate new `alt` text written to match what the replacement image actually shows (not left describing the old photo). After all replacements, the same audit command must return zero output, and a bulk `xargs -P N curl -o /dev/null -w '%{http_code}'` sweep over every unique URL must show 100% `200`.

**New rejects found while sourcing ~40 replacement photos** (beyond the watermark/404 lessons already recorded above):
- Several "clean-sounding" bakery/pantry candidates turned out to have a competing real bakery's **branded packaging, signage, or a name/logo baked into the shot** once actually viewed (a "Josey Baker Bread"-branded paper bag; a wall-sized "Rocco Princi" bakery mural with "STARBUCKS RESERVE" watermarked into the corner; a hand-lettered German-language chalkboard sign with zero food visible). - A bakery display-case candidate had **visible foreign-currency (€) price tags** baked into the shot ("Croissant 1.00€") — not a competing brand, but a content-accuracy mismatch for a USD-priced Ontario store; discarded for the same reason a mismatched caption would be.
- **Lesson reinforced at larger scale:** when sourcing many replacement photos quickly under time pressure, the failure mode shifts from "wrong subject" (the earlier T1/T2 lesson) to "right subject, wrong background details" — a photo can accurately show bread, croissants, or pantry jars and *still* be unusable because of an incidental price tag, chalkboard, or logo elsewhere in the frame. Bakery and prepared-food-display photography is disproportionately likely to include this kind of incidental real-world signage compared to plain produce/product-on-a-surface shots — budget extra verification passes specifically for that category.

**Bugs caught during this pass (scripted-test + visual-review, before sign-off):**
1. **Tailwind's CDN-injected utility stylesheet silently defeated a custom display-toggle class due to cascade order, not specificity.** `.aisle-panel { display: none } .aisle-panel.is-active { display: grid }` looked correct and the `initAisleTabs()` JS was toggling `is-active` correctly (confirmed by inspecting `classList` directly) — but every panel remained visibly `display: grid` regardless, because each panel `<div>` also carried Tailwind's own `.grid` utility class for its internal layout, and the Tailwind CDN script injects its generated `<style>` block into `<head>` *after* `style.css` has already been parsed (it runs synchronously and appends at the point the script tag was declared, while `style.css` is a `<link>` earlier in the same `<head>`), so `.grid` — same specificity as `.aisle-panel`, later in source order — won the cascade. Caught by a Puppeteer test that read `getComputedStyle(panel).display` before any tab was ever clicked and found it was already `"grid"` for a non-active panel. **Fix:** raised the hidden-state selector's specificity instead of reordering markup or adding `!important` — `.aisle-panel:not(.is-active) { display: none }` (two-part specificity, `0,2,0`) reliably beats `.grid` (`0,1,0`) regardless of load order. **Lesson: any custom CSS class that toggles `display` on an element which *also* carries a Tailwind display-utility class (`.grid`, `.flex`, `.block`, etc.) for its internal layout is racing the Tailwind CDN script's injection timing — don't rely on source order or equal-specificity single-class selectors to win; use `:not(.state-class)` or an equivalent higher-specificity selector, not `!important`, on the hidden-state rule.** A `getComputedStyle` check on the *unclicked* default state (not just the post-interaction state) is now the standard test for any new show/hide toggle feature going forward.
2. **Passing `navigation: undefined` to the Swiper constructor threw `Cannot read properties of undefined (reading 'enabled')` on every page load**, even though the intent ("only enable custom navigation for swiper instances that actually have matching buttons") was reasonable. Swiper 11's internal param-merging does not tolerate an explicitly-`undefined` value the same way it tolerates the key being absent entirely. Caught by a scripted `pageerror` listener (not visible without one — the carousels still rendered and functioned, autoplay included, so this was a silent-but-real console error, not a UX-visible bug). **Fix:** build the Swiper config object conditionally — only assign `config.navigation = {...}` when both button elements exist, never assign the key to `undefined`. **Lesson: when a library's config object is being built conditionally, omit optional keys entirely rather than assigning them a falsy/`undefined` placeholder — many libraries (Swiper included) distinguish "key absent" from "key present but undefined" internally and only the former is safe.**
3. **Two Swiper carousels' autoplay silently never advanced because they had exactly as many slides as the carousel's largest `slidesPerView` breakpoint, leaving nothing to scroll to** — the *same root cause* as the `loop`-missing bug fixed earlier in this template's history, but manifesting differently: `.testimonial-cards-swiper` (3 slides) and `.farmers-swiper` (4 slides) both sit under the shared `.offers-swiper` config, whose widest breakpoint shows 4 slides at once (`1280: { slidesPerView: 4 }`). With slide count ≤ `slidesPerView`, every slide is already visible simultaneously and there is nothing for `activeIndex` to advance to, regardless of `loop`/`autoplay` settings — confirmed via the same multi-sample `realIndex`-over-8-seconds technique used for the original bug, which returned `0,0,0,0` for both. **Fix:** added one additional testimonial and one additional farmer card to each (bringing both to 5, matching the `loop: slideCount > 4` threshold already established elsewhere in `initSwipers()`), re-verified with the same sampling technique returning genuine progression (`0,1,1,2`). **Lesson: any carousel sharing a common Swiper config with other instances needs its own slide count checked against *that config's maximum `slidesPerView` breakpoint*, not just checked for "more than one slide" — a carousel can have multiple slides and a working `loop` setting and *still* never move if the viewport-appropriate `slidesPerView` happens to equal or exceed the slide count.**
4. **Six replacement Unsplash photo IDs sourced for this pass returned HTTP 404 in production despite the search-result page listing them as live results**, three of them additionally surfacing as `net::ERR_BLOCKED_BY_ORB` in Chrome (Opaque Response Blocking triggers when a cross-origin `<img>` request's response isn't actually image content — consistent with the CDN returning an HTML/JSON error body for a dead photo ID). Because `idx` is a single mutable variable shared by every closure (not a fresh per-call binding), by the time that `setTimeout` actually fired 500ms later, `idx` had already been reassigned to `next`'s value — so the cleanup callback ran against the *new current* span instead of the *old departing* one, permanently stacking a leftover `is-waiting` class (`opacity: 0`) onto the span that was simultaneously carrying `is-current` (`opacity: 1`). This had been silently broken since the feature was introduced and simply hadn't been caught because prior screenshot-based visual QA happened to sample the hero before the first ~2.6s rotation completed. Re-verified with the same multi-sample technique across 12 samples / 6 seconds / 3 full rotations on both Home 1 and Home 2: exactly one span visible at all times, correct word at each expected interval. **Lesson: any `setTimeout`/`setInterval` callback that closes over a shared, later-reassigned loop/state variable (`idx`) rather than a value captured fresh at invocation time is a latent bug even when it "looks fine" in a quick visual check — this class of bug is specifically inclined to hide from screenshot-based QA (which naturally tends to sample near page-load, before enough animation cycles have elapsed to surface it) and needs an explicit multi-sample-over-time test, not a single screenshot, to catch.**

**Container/alignment re-audit — a testing-methodology lesson, not a template bug:** the first automated pass of this audit falsely flagged every content container on every page as misaligned (`leftMismatch`/`rightMismatch` > 0 everywhere). Root cause was in the *test script*, not the site: it compared each `.max-w-\[1440px\]` container's own unpadded `getBoundingClientRect().left` (which is legitimately `0` at the viewport's exact max-width, since the container itself has no left offset before its own `px-4`/`px-6` padding is applied) against the header **logo's** rendered position (which is *already* inset by the header's identical container's padding). This is an apples-to-oranges comparison — a padded child position vs. an unpadded parent-container position — and would flag a false mismatch on a perfectly correct page. **Corrected methodology:** compute each container's *padded content edge* (`rect.left + computedPaddingLeft`, `rect.right - computedPaddingRight`) and compare that to the logo/last-button positions, since both sides of the comparison are now "where content visually starts/ends," not a mix of container-edge and content-edge measurements. Re-run with the fix across all 8 pages at 1024/1440/1920px: **zero mismatches everywhere** — the container system was already correct going into this pass; no site changes were needed here. **Lesson: when an automated geometry audit reports every single page as broken (100% failure rate on a system that passed manual/visual review repeatedly in prior passes), suspect the test's comparison logic before the site — a measurement bug that compares two different "kinds" of edge (padded vs. unpadded, content-box vs. border-box) produces exactly this kind of uniform false-positive across every page, whereas a real template regression would typically affect specific pages or sections inconsistently.**

**Bugs caught and fixed while building it (scripted-test + visual-review, before sign-off):**
1. **Nested a `<button>` inside an `<a>` in an early draft of the spotlight card** (to make the whole card a link to `categories.html#produce` *and* keep the "Add to list" button inside it). This is invalid HTML — a `<button>` is not permitted as a descendant of an `<a>`, and browsers silently "fix" the malformed markup via the HTML parser's adoption-agency algorithm, which can rearrange the DOM in ways that break event handling unpredictably. Caught before ever loading the page, by re-reading the markup just written rather than only trusting the visual screenshot. **Fix:** changed the spotlight's outer element from `<a>` to a plain `<div>`, matching the established `tag-card` pattern used by every other product card site-wide (a non-link container with the `data-add-to-list` button as its real call-to-action) — consistent with the rest of the template rather than a one-off exception.

Because `overflow-x: hidden` on `html`/`body` (added in an earlier pass specifically to prevent this class of bug from producing a page-wide horizontal scrollbar) was doing its job, `document.documentElement.scrollWidth` reported **zero** overflow even while the spotlight card and list rows were visibly clipped mid-content on screen (the "Add to list" button and a price figure cut off at the viewport edge) — a real, visible defect that a naive `scrollWidth`-only overflow check would have completely missed. Re-verified: grid track now correctly sizes to 358px (matching its container) at 375/390px widths, with zero overflow at both the element level and the document level, and correct behavior confirmed right at the `lg:` (1024px) breakpoint boundary from both sides (1023px and 1024px). **Lesson: `document.documentElement.scrollWidth <= clientWidth` is *not* sufficient proof that nothing is visually overflowing once a page has a global `overflow-x: hidden` safety net — that net converts a page-wide scrollbar bug into a silent content-clipping bug instead, which is arguably worse (invisible in the one check most likely to be run). Any new CSS Grid or Flexbox layout with fixed-size children (thumbnails, icons, buttons) sitting alongside a `flex-1`/shrinking text element needs `min-w-0` on the shrinking container(s) as a matter of course, and should be verified with an element-level `getBoundingClientRect()` check at the narrowest supported viewport, not just a document-level scrollbar check.**

**Image sourcing at scale:** rather than sourcing all 72 images from scratch, the ~40 individual product photos removed from `categories.html` and `offers.html` during the fifth pass's simplification (and still sitting unreferenced anywhere on the live site) were re-identified from this session's own history, re-verified as still unused and still HTTP 200, and reused as a 39-image head start — cutting the fresh-sourcing requirement to 33 new photos across the 6 categories. **Bugs found and fixed during this pass (before sign-off):**
1. **The "All" filter showed all 72 products instead of a curated 12**, because `initCategoryFilter()`'s matching logic was `value === 'all' || cats.indexOf(value) !== -1` — a hard-coded special case that always treats `"all"` as "show everything, unconditionally," a holdover from every earlier use of this function where "All" genuinely meant "no filtering." That assumption broke as soon as "All" needed to mean "show this specific curated subset" instead. Caught immediately by a scripted click-through test that asserted the visible count after every filter button, not just spot-checking one or two. **Fix:** removed the special case entirely — `data-filter-item="produce all"` on 2 items per category makes `"all"` a literal tag like any other, matched the same way as `"produce"` or `"dairy"`. Verified: `all` → 12, and each of the 6 aisle filters → 12, with the 4-column grid confirmed via `getComputedStyle`. **Lesson: a shared filter utility's "match everything" special case is only safe as long as every consumer actually wants that behavior — the moment any one usage needs "all" to mean a specific subset rather than "no filter," the special case must be removed for every consumer, not special-cased further, since a per-page override would silently reintroduce the same bug the next time the function is reused.**

This is the same "branding risk scales with display size" lesson recorded in the seventh pass, now confirmed as a recurring, not one-off, failure mode for this template — **any image being reused from an earlier, smaller placement must be re-verified at its new size before reuse, every time, not just the first time this lesson was learned.** Replaced with a close-up vine-tomato photo with no signage, re-verified clean, unique, and HTTP 200.
3. Two further candidates were pre-emptively rejected during initial sourcing before ever reaching the page: an olive oil bottle shelf with a real, legible Spanish brand ("Rafael Salgado — Packed in Spain") repeated across every bottle in frame, and an artisan candle with legible product-label text ("Poured by Fi — Calmness") — a small/independent brand rather than a national one, but still real, legible product branding, treated as disqualifying under the same standard regardless of the brand's size or recognizability. Both were swapped for clean alternatives (a spice-spoon shot for the pantry slot, a plain unlit taper candle for the household slot) before either was ever committed to a page, consistent with the project's now-standard fetch-then-Read verification step running *before* an image is written into HTML, not as a post-hoc audit.

All ~15 `premium_photo-` URLs already live across the site (14 in `categories.html`, 1 testimonial avatar in `index.html`) were confirmed watermarked by spot-checking two of them, then all 15 were replaced with re-sourced, fetch-then-Read-verified `images.unsplash.com/photo-*` (standard, non-Plus) equivalents matching each original subject/alt-text as closely as possible, with two intentional near-substitutions where a truly clean match for the literal subject couldn't be found without a defect (a rolled-towels photo standing in for "laundry detergent bottle," and a 4-candle photo standing in for the described metal-holder single candle) — alt text was rewritten in both cases to accurately describe what the replacement image actually shows, rather than leaving a caption that no longer matched. **Lesson for all future templates: `plus.unsplash.com` (Unsplash+/premium) URLs must be treated as never-safe-to-use without a paid license, full stop — not just "verify like any other image." Restrict all sourcing to `images.unsplash.com/photo-` (standard) URLs going forward, and if a `plus.unsplash.com` URL is ever found already in a project, assume it's watermarked and replace it rather than spot-checking a sample and hoping the rest are fine — the failure mode is invisible to every automated check this project already runs.**

**Image sourcing:** 6 new photos (Shop by Craving), 7 new photos (Fresh Picks Gallery), 4 new photos (Home 2 hero strip), plus 15 replacement photos (watermark fix) — 32 total, every one sourced via `WebFetch` on Unsplash search-results pages and verified via the fetch-then-Read technique before use. Final sweep: 114 unique image URLs site-wide, zero duplicates, 100% HTTP 200, zero `plus.unsplash.com` references remaining anywhere in the template.

### shop.html follow-up — broken sidebar filter, full photo catalog, 3×3 pagination
A direct follow-up flagged three problems with the redesigned `shop.html`: the sidebar occasion filter was unreliable ("not working properly"), the mixed photo-card / icon-only-row layout read as inconsistent, and the user wanted every product photographed, a 3×3 (9-per-page) grid, and pagination.

**Root cause of the flaky sidebar filter:** the occasion-filter chip wrapper carried `data-scroll-strip`, which attaches the site's generic horizontal-drag-scroll handler (`initHorizontalScrollStrips()` — wheel-redirect + `setPointerCapture` drag-to-scroll, built for wide content carousels like testimonials/best-sellers). That handler calls `strip.setPointerCapture(e.pointerId)` on every `pointerdown` anywhere inside the strip, including presses that land on a child `<button>`. Capturing the pointer on the parent, combined with any sub-pixel movement between press and release (extremely common on trackpads/touch), is a well-documented way for a scrollable container to swallow taps on its own interactive children. **Fix:** removed `data-scroll-strip` from both the occasion-filter wrapper (`shop.html`) and the gallery-filter wrapper (`gallery.html`, same latent bug, fixed proactively) — neither needs the custom mouse-drag assist: on desktop the sidebar is `lg:flex-col lg:overflow-visible` (nothing to scroll), and on mobile/tablet native touch/trackpad scrolling on a plain `overflow-x-auto` row works with zero JS. **Lesson: never attach a drag-to-scroll/pointer-capture handler to a container whose children are themselves clickable controls (filter chips, tab buttons) — reserve `data-scroll-strip` for passive content strips (cards, testimonials, images) with no interactive elements inside the scrollable area.**

2. **Two real bugs found and fixed during visual QA (headless-Chrome screenshot review, see tooling note below):**
   - The in-flow mobile push-panel (`#mobile-panel`, `grid-template-rows:0fr→1fr`) left a hairline sliver of its closed content (the "Home" accordion row) visibly bleeding in under the header at rest. Root cause: a `0fr` grid track doesn't reliably reach a true zero rendered height across engines when its content has any intrinsic line-height. Fixed by pairing the height transition with a `visibility` toggle that's delayed on the *closing* edge only (`transition: grid-template-rows .35s ease, visibility 0s linear .35s` at rest vs. `0s linear 0s` when `.is-open`) — content stays visible through the collapse animation, then fully leaves the render tree, so a fractional leftover row height can never paint.
   - The hero's image column (`grid lg:grid-cols-2` → single column below `lg`) had no `min-w-0` on the flex/grid items wrapping the `<img>`; a flex/grid item's default `min-width:auto` lets a replaced element's intrinsic size force the whole shared implicit grid track wider than the viewport, which cascaded into the header's own icons appearing to be pushed off-screen and the H1 failing to wrap on narrow widths — despite the header itself being unrelated to the hero. Fixed by adding `min-w-0` to the hero's left/right grid children and the image's flex wrapper. **Lesson for future templates: any flex/grid item that contains an `<img>` (or other replaced element) needs an explicit `min-w-0` unless the item is also given a hard `width`/`max-width` — the default `min-width:auto` floor is sized from the image's intrinsic pixels, not from its `w-full`/percentage CSS width, and the resulting overflow can visually manifest on a completely unrelated sibling (here, the sticky header) rather than on the offending element itself.**
   - Separately (not overflow-related): `initReveal()`'s `IntersectionObserver` used `threshold:0.15` + a `-40px` bottom `rootMargin`, so content already sitting in the initial viewport at load (e.g. the third "Shop by Category" card, at 1440×~1000) could sit at just-under-threshold intersection and never receive a first callback, leaving it permanently at the base `[data-reveal]{opacity:0}` state. Fixed by checking each `[data-reveal]` element's `getBoundingClientRect()` against the viewport at init time and snapping anything already visible straight to its revealed end-state (`duration:1`, no stagger delay) instead of routing it through the observer at all — scroll-triggered animation is now reserved for content that's genuinely below the fold at load, which is both more correct UX (nothing "waits" to appear if the user never scrolled past it) and eliminates the class of flakiness entirely rather than just tuning the threshold numbers.
   - A third, independent bug surfaced while testing the Visit Us card's live status pill: `initHoursStatus()` opened with `if (!rows.length) return;` against `[data-hours-day]` (the *hours-table* row-highlighter), which unconditionally skipped the rest of the function — including the unrelated `[data-open-status]` Open Now/Closed Now badge logic — on every page that has the badge but not the full hours table (`index.html`; `contact.html` has both and was never affected). The badge had silently rendered as an empty `&nbsp;` pill since initial launch. Fixed by making the hours-table block conditional internally instead of an early return that aborts the whole function.

### Post-launch fixes (logged so future templates don't repeat the same mistakes)
1. **Tailwind-CDN-vs-custom-CSS cascade race:** `.card-pizza` originally set `padding-top:4.25rem` in `style.css` while every card also carried Tailwind's `p-5` utility (which also sets `padding-top`) in its class list. Because Tailwind's CDN script JIT-injects/re-injects its generated stylesheet at an unpredictable point relative to when the page's own external `<link rel="stylesheet">` parses, the two same-specificity same-property rules raced — and lost the porthole photo's intended vertical clearance, causing the card title text to render *underneath* the porthole image on every single pizza card, at every breakpoint (confirmed via full-page screenshot testing, not just a spot check). **Fix:** removed the competing `padding-top` from the custom class entirely and set the clearance via a Tailwind arbitrary-value utility (`pt-[4.5rem]`) directly in the HTML instead, so there is only one source of truth for that property and no cross-stylesheet race is possible. **Lesson: never let a custom CSS class and a Tailwind utility class set the same CSS property on the same element when using the Tailwind CDN build — the load order between the CDN's injected styles and any external stylesheet is not guaranteed, so whichever "should" win by source order is not reliable.**
2. **Responsive nav dead zone (768–1279px):** the initial header only implemented two nav states — full inline nav at `xl`+ (1280px) and the bottom tab bar below that — leaving tablet widths (768–1279px) with *no* way to reach primary nav links from the header at all (bottom tab bar was also hidden at that width in a later fix pass, compounding it). **Fix:** added a third `tabletMenuBtn`/`tabletMenuPanel` hamburger-dropdown pair (`hidden md:flex xl:hidden`) containing all 8 site links, scripted into every page via a batch find/replace anchored on the header's closing `</div></div></div></header>` sequence, and narrowed the bottom tab bar's visibility from `xl:hidden` to `md:hidden` so it no longer doubles up with the new tablet panel. **Lesson: a `hidden xl:flex` + "everything else gets the mobile pattern" binary is not enough once the desktop breakpoint is pushed as high as `xl` (1280px) for a 5+ item nav — always explicitly design and test the intermediate tablet band (768–1279px) rather than assuming the mobile pattern scales up to fill it.**
3. **Card grid too dense at `lg` (1024px):** `.card-pizza` grids jumped straight from 2 columns (`sm`) to 4 columns (`lg`, 1024px), which combined with fix #1's overlap bug made tablet-width cards unreadable; even after fix #1, 4 columns at exactly 1024px was still visually cramped. **Fix:** changed the breakpoint to `sm:grid-cols-2 xl:grid-cols-4` (skipping straight from 2 to 4 columns only at 1280px+), giving 2-column cards the full tablet range to breathe.
4. **Image content-mismatch audit:** an initial pass of "confident" Unsplash photo-id guesses was checked only for HTTP 200 (not visually), which caught outright 404s (6 ids across menu.html/home-2.html) but missed at least one id that returned 200 while depicting a completely unrelated subject (a restaurant interior used for a "BBQ Chicken Ember" pizza card and, separately, for a "pizza being topped" process photo). **Fix:** every photo id actually used on the site (38 total) was downloaded and visually inspected via the Read tool before finalizing, not just curl-status-checked. **Lesson: a 200 status code confirms a URL resolves, not that the image matches its `alt` text or surrounding content — for any template where specific subject matter matters (a named menu item, a labeled process step), spot-check the actual pixels, especially for ids chosen from memory rather than a live search.**
5. **Missing `data-accordion-trigger` on `index.html`'s FAQ-preview accordion:** the buttons carried the `.accordion-trigger` *class* (for styling) but not the `data-accordion-trigger` *attribute* that `main.js`'s `initAccordion()` actually queries for (`document.querySelectorAll('[data-accordion-trigger]')`), so the three FAQ-preview questions on the homepage were visually styled correctly but completely inert — clicking them did nothing. Caught by a parallel background agent building the site's other pages, which correctly included the attribute on its own 21 FAQ-page accordions and flagged the homepage's omission. **Lesson: a component's *style* hook (class) and its *behavior* hook (data-attribute) can silently drift apart when a card/accordion/tab pattern is hand-copied across sections instead of generated from one template — grep for the JS's actual selector strings across every page after any hand-copy, don't just visually confirm the styling looks right.**

### Site-wide fix — card/thumbnail photos cropping out the top of the subject
A direct bug report: images "cut at top," narrowed down via a clarifying question to specifically the small card/thumbnail photos (not hero banners, not anchor-scroll behavior).

1. **Root cause:** every `object-cover` thumbnail defaulted to the browser's `object-position: 50% 50%` (dead center), with no CSS anywhere in the project overriding it. That's invisible as long as a photo's source aspect ratio is close to its container's — but several fixed-height card boxes (deals.html's `h-48` combo cards, home-2.html's `h-56`/`h-64` category tiles and ingredient photos) are much shorter/wider than the source photos being cropped into them. Measured example: the Family Feast deal card is a `384×192` box showing a `700×1050` source photo — `object-fit:cover` scales that image up until it fills the box width, which pushes the rendered height to ~576px, meaning **only the center 33% of the photo's height was ever visible** at 50/50 position. Center-cropping a photo that's 3× taller than its frame reliably slices off whatever was in the top third — which for people-and-food photography (hands, faces, the actual dish) is usually exactly where the subject is.
2. **Fix:** changed `object-position` from center to top (`object-top` / `object-position:top`) on every card/thumbnail image identified as a genuine subject-photo — `.side-card img` and `.kid-card img` and `.popular-swiper img` (menu.html, added as shared CSS rules), `.gallery-tile img` (gallery.html), the 3 deal combo cards + 1 upcoming-deal preview (deals.html), the 4 category tiles + 2 ingredient photos + 4 "oven to door" process-strip photos (home-2.html), and the Family Feast deal-preview photo (index.html) — 20 images total. **Deliberately left untouched:** every full-bleed hero/banner image (confirmed not the issue), the JS-driven Signature-spotlight display and its selector-row thumbnails (same reasoning — large "hero-like" feature display, not a plain grid thumbnail), and every circular face photo — testimonial avatars, the hero's "loved by" avatar stack, and About's `.team-card` portraits — since biasing a headshot crop toward "top" risks cutting off chins instead of fixing anything; center is the more reliable default for photos where a person's face is already the intended focal point.
3. **Verification:** measured `naturalWidth`/`naturalHeight` vs. rendered box size via Playwright for the worst-offending cards before concluding this was really an aspect-ratio/crop-math issue and not a lazy-loading or broken-image artifact (two red herrings ruled out during triage: a `loading="lazy"` image that simply hadn't finished loading by the time a test screenshot fired looks nearly identical to a genuinely blank/broken image — always re-check with a longer wait or a forced `scrollIntoView` before concluding an image is broken); screenshotted the Family Feast card before/after and confirmed the crop changed from a bland close-up of plain melted cheese to the intended "hands cutting into a fresh pizza" action shot; re-verified all 20 touched images still return HTTP 200 after editing (no accidental URL corruption from the batch find/replace); confirmed zero console errors and no regressions in dark mode or RTL across every page touched.

**Lesson:** `object-fit:cover` with the browser's default center position is only safe when a container's aspect ratio roughly matches its source photos. Any card/thumbnail component with a **fixed pixel height** (`h-48`, `h-56`, `h-64`, etc.) spanning a **variable-width** grid column is a standing risk — the effective aspect ratio changes with viewport width, and the source photos for a template like this are sourced from Unsplash with no consistent aspect ratio of their own. Default new "card row" and "tile" image components to `object-position:top` from the start for food/product/lifestyle photography (not faces), rather than discovering the crop is wrong per-image after the fact.

### `menu.html` + `desserts.html` — "standard UI/UX" pass (reverts the card-variety experimentation above)
A direct follow-up explicitly asking for "standard UI/UX" on these two pages — a course correction after several rounds of increasingly bespoke per-section layouts (portfolio-card feature grids, full-bleed banner tiles for Vegan, compact circular-thumbnail list-rows for desserts) left the pages feeling inconsistent/unfamiliar rather than polished. Recorded distinctly from the entry above because it's a deliberate *reversal* of some of that work, not an extension of it — future templates should read both entries to understand why the design changed direction mid-project.

1. **New shared component — `.menu-card` (`style.css`):** the conventional food-delivery-app product card every major real-world reference (DoorDash, UberEats, Grubhub, typical restaurant WordPress themes) actually uses — a fixed `4/3` `object-fit:cover` photo (not the `.portfolio-card`'s letterboxed `contain`), a bold title, a 2-line `-webkit-line-clamp` truncated description, and a footer row (price + round add-button) separated by a hairline divider. This is a **deliberate reversal** of the "never crop a portfolio card" policy established two entries above — cropping to a consistent aspect ratio is what "standard" food-menu UI actually looks like; the letterboxed/uncropped treatment, in hindsight, read as unusual rather than premium once multiple sections used it side by side. `.menu-card` is now the single card component for every product grid on both pages — no per-section visual variation (no large-vs-small card sizes, no card-vs-banner-vs-list mixing) — because *predictability across categories* is precisely what "standard UI/UX" means for a menu: a user should be able to tell at a glance that Signature, Classic, Vegan, and Kids are all "the same kind of thing" (a pizza you can order), not visually-distinct product families.
2. **`menu.html` changes:** Signature Pizzas, Classic Pizzas, and Vegan & Plant-Based were unified onto the same `.menu-card` grid (4-across on desktop, all three sections now visually interchangeable except content) — Vegan's full-bleed banner-tile treatment (logged above) was removed entirely, since a single 2-card section styled completely differently from its neighbors was the opposite of "standard." Kids Menu and the "Popular This Week" Swiper carousel kept their existing markup (both were already close to `.menu-card`'s shape) but had their `object-fit:contain !important` CSS overrides deleted so the pre-existing `object-cover` Tailwind classes on their `<img>` tags could apply normally — a two-line CSS deletion instead of a markup rewrite, since the HTML structure didn't need to change, only which fit mode won the cascade. Sides & Salads (compact horizontal list-row) and Dips & Extras (small icon chip grid) were deliberately left unchanged — a smaller-footprint list for "add-on" items and an icon-only chip row for condiments are themselves standard, recognizable patterns for those specific content types (modifier/add-on UI in real ordering apps looks exactly like this), so "standard" didn't mean "make everything identical," only "don't invent a bespoke layout per product category."
3. **`desserts.html` changes:** all four item sections (Signature Desserts, Gelato & Frozen, Cookies & Sweet Bites, Seasonal Specials) were converted from the `.dessert-list`/`.dessert-row` compact list (circular thumbnail + text row) to the same `.menu-card` grid used on `menu.html` — consistent card language across both ordering pages of the site now, not just within each page. The asymmetric list+photo-panel layout added to Gelato and Cookies in the previous round (to fill leftover whitespace next to a `max-w-2xl`-constrained list) was removed outright rather than adapted, since a plain `.menu-card` grid fills the full container width on its own and no longer needs a filler panel — the whitespace problem and its fix both disappeared once the underlying list layout was replaced. The Dessert-of-the-Month spotlight banner (a standard "featured item" hero pattern) and the Dessert Pairings cross-sell widget (a standard compact "goes great with" card) were left as-is — both are already conventional, recognizable UI for their purpose and weren't part of what made the page feel non-standard.
4. **Removed CSS, not just unused-in-markup:** unlike earlier rounds where a superseded component was left defined in `style.css` in case another page still used it, `.dessert-list`/`.dessert-row`/`.dessert-row-*` were deleted outright from `desserts.html`'s own `<style>` block (they were page-scoped, not shared) since a `grep` confirmed zero remaining references anywhere in the project before deleting — the `.portfolio-card` family, by contrast, was left in the shared `style.css` even though this pass stopped using it on `menu.html`, since it's still a valid pattern that could be revived elsewhere.

**Do not reuse for future templates (additions):** `.menu-card` standard e-commerce product card (cover-crop photo, clamped description, price+button footer) as *the* baseline "boring but correct" card for any future template that wants a conventional menu/product-listing feel — reserve `.portfolio-card`'s uncropped/letterboxed treatment for templates where showing a photo's true proportions is the actual differentiator (a photography portfolio, real estate listings), not for food/product cards where audiences expect a cropped, consistent thumbnail.
